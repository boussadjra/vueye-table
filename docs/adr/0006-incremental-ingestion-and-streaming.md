# 0006 — Incremental ingestion and streaming sources

Status: accepted. Implements #73, coordinated with ADRs 0003, 0011 and 0012.

## Decision

`appendData`, `upsertData` and `removeData` are source operations, distinct from undoable user row operations. They return frozen `DataIngestionResult` counts and issues, publish through `onDataChange(data, [])`, and do not create pending-save records or undo steps. Ingestion requires stable keys. Duplicate append keys, repeated keys in a batch, invalid keys and source callback failures recover as issues; valid independent rows can apply. Incoming key functions must not depend on changing row positions.

Unsorted flat append indexes and filters only new rows. Read-only chunked array views publish concatenated data and lazily projected snapshot rows without copying the old dataset. Sorted append sorts incoming matches and stably merges them with the prior order, with existing rows winning ties. Page/selection changes reuse pipeline results. Full iteration/materialization still costs O(n); expanded detail enumeration, changed query/columns, upserts/removals and hierarchical rebuilding may also visit existing rows. Tree processing preserves sibling/ancestor semantics through the existing tree engine; the flat append budget does not promise incremental hierarchical filtering.

Local edits are allowed during a stream. Upsert/removal refuses a row or affected tree branch with unsaved changes or pending validation using `ingestion_conflict`. Local removed-key tombstones also prevent reinsertion. Callers save/revert, then retry or explicitly replace foreign data; core never silently selects a conflict winner. Unrelated source rows continue to apply. Source removals prune retained batches and selection for deleted keys. Structural user batches are rebased over incoming source changes, so undo/redo cannot discard newly received data. Cell undo retains its recorded user values and makes a new pending change against the current source baseline after an acknowledged save.

Nested upserts address keys, require `setChildren` for child writes, preserve loaded children when omitted, and replace children when explicitly supplied. Adjacency input may reparent source-owned rows only if the candidate tree remains valid. Lazy children retain their injected cancellation/caches; source operations do not reparent a cached lazy child. New tree recovery problems reject the candidate atomically. A removed parent removes its loaded subtree.

`stream(source, { signal?, batchSize?, expectedRowCount?, mode? })` accepts an async iterable yielding rows or row arrays. Arrays denote batches. Each source yield is split into bounded batches (default 1,000) with a microtask between publications; backpressure waits for each publication before reading again. A new run supersedes the previous run. Structural signals with abort listeners interrupt a blocked `next()` immediately; polling-only signals are observed at source/batch boundaries. Foreign `setData` and disposal cancel the active run. Late results cannot modify data or load metadata. Cancellation requests iterator cleanup without awaiting an uncooperative `return()`.

Snapshots expose `idle`, `loading`, `streaming`, `done`, `error` or `aborted`, loaded source-row count before filtering, and an optional caller-provided expected count. Stream results report accepted top-level incoming records, completion status and issues. A source error preserves received rows and reports `stream_error`; recovered ingestion conflicts do not stop the source. Hints come only from callers; core has no transport, DOM or Node dependency. Own-array `setData` round trips preserve the source and pending edits. `useDataTable` forwards operations and metadata; transport adapters, frame coalescing, infinite-scroll controls and component load presentation remain #74.

## Consequences

Consumers receive arrays through the existing readonly contract. Mutation is refused on ingestion views; use `Array.from(data)` when a mutable copy is needed. The runnable core example and flat append benchmark record these boundaries. `UndoStack.transform` atomically reconciles or removes retained batches without recording a user action. Source ingestion does not replace application authorization, sanitization or server validation.
